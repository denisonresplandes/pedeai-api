## Arquitetura utilizada

Clean Architecture + CQRS leve + DDD leve (domínio rico). É uma escolha deliberada: o curso usa arquitetura em camadas tradicional.

```
presentation  →  core.application  →  core.domain
infrastructure →  core.application  →  core.domain      (setas = "depende de")
```

| Camada | Pacote | O que tem | Regra |
|---|---|---|---|
| Domínio | `core.domain` | Aggregates (`Kitchen`, `Restaurant`, `Payment`), VOs (`KitchenId`, `KitchenName`, `Money`...), portas de escrita (`*Repository`), `DomainException` | Java puro: sem Spring, JPA ou Jakarta. Guarda as invariantes. |
| Aplicação | `core.application` | `*CommandHandler` (escrita; **interface** com a implementação `Default*CommandHandler`), `*QueryHandler` (leitura), `*Command`, `*Response` (também o modelo de leitura), portas de leitura (`*QueryRepository`), exceções de aplicação, portas de saída (`PaymentProcessorStrategy`) | Java puro: sem anotações do Spring (nem `@Service`/`@Transactional`). Handlers são montados em `infrastructure/configs/*Config`; a transação é aberta pelo decorator `infrastructure/transaction/Transactional*CommandHandlerDecorator`. |
| Infraestrutura | `infrastructure` | Entities JPA, mappers, adapters das portas, Spring Data, gateways (Stripe, MercadoPago, Cash), configs | Implementa as portas do core. |
| Apresentação | `presentation` | Controllers, `*Request` (Bean Validation), `GlobalExceptionHandler` | Traduz HTTP ⇄ Command/Response. |

Padrões em uso:
- **CQRS leve:** `*CommandHandler` + `*Repository` (porta no **domínio**, fala em aggregate e VOs) para escrita; `*QueryHandler` + `*QueryRepository` (porta na **aplicação**, devolve o `Response`, nunca o aggregate) para leitura.
- **Tipos nas portas de leitura:** retorno é sempre o modelo de leitura (`Response`). O critério de busca (`name`) é `String`, não VO: um termo de busca não é um "nome válido" (a busca por `a` deve dar "não encontrado", não "nome curto demais"). Id pode ser `Long` ou o VO, conforme o chamador. As portas de escrita usam VOs.
- **Aggregate:** construtor privado, `create(...)` (sem id) e `restore(...)` (com id, usado só pelo mapper da infra). `equals` por id, `hashCode` constante.
- **Referência entre aggregates por ID** (`Restaurant` guarda `KitchenId`, não `Kitchen`).
- **Ports & Adapters:** `XRepositoryAdapter` converte `Entity ⇄ domínio` com `XMapper` e delega ao Spring Data.
- **Erros:** `DomainException` → 400, `ValidationException` → 400, `ResourceNotFoundException` → 404, `ConflictException` → 409, todos como `ProblemDetail`.

Regra de ouro: **todas as classes em `core.*` (domain e application) são Java puro, sem anotações do Spring** (nem Jakarta/Hibernate). `core.domain` nunca importa `application`, `infrastructure` ou `presentation`; `core.application` nunca importa `infrastructure` ou `presentation`. Verificado em 2026-10-23: nenhum import de framework em `core`.

### Fase 3 — Arquitetura
- [x] **16. Transação por caso de uso.** Decorator manual na infraestrutura (decisão do usuário, por ser mais rastreável que um advisor/proxy): cada `*CommandHandler` virou **interface** (a costura) com a implementação `Default*CommandHandler` (só regras, sem transação); `infrastructure/transaction/Transactional{Kitchen,Restaurant,Payment}CommandHandlerDecorator` implementa a mesma interface e embrulha cada método com `TransactionTemplate` (`execute` / `executeWithoutResult`: COMMIT se o handler volta, ROLLBACK e a mesma exceção sobe se lança `RuntimeException`; todas as exceções do projeto são `RuntimeException`). Os `*Config` criam o `Default*` e expõem **só o decorator** como bean (se o handler também fosse bean, o controller poderia receber o handler sem transação). As consultas (`*QueryHandler`) ficam sem transação, de propósito: cada uma é uma chamada só e já devolve o `Response`. Saíram os `@Transactional` dos controllers (Kitchen update/delete, Payment, webhook) e do `RestaurantRepositoryAdapter.findById`. - [x] **17. (B10)** `DefaultPaymentCommandHandler.processPayment` agora faz, nesta ordem: (1) cria o `Payment` (só domínio, valida) e escolhe a estratégia; (2) grava o pagamento `PENDING`; (3) chama o gateway. Um método sem estratégia é recusado (400) **antes de qualquer ida ao banco** (antes gravava e dependia do rollback para desfazer). O `processPayment` deixou de rodar dentro de transação: o `TransactionalPaymentCommandHandlerDecorator.processPayment` só repassa a chamada (de propósito, comentado), e o `save` tem a própria transação curta, que termina (commit) antes do gateway; o `confirmPaymentFromWebhook` continua transacional. **Decisão sobre falha do gateway:** o pagamento já está gravado `PENDING` e a exceção sobe ao cliente; **não marca `FAILED`**, porque uma falha de rede não diz se o gateway chegou a processar o pedido, e o webhook `SUCCESS` que viesse depois seria recusado em um pagamento `FAILED` (ver B11). Antes, a falha desfazia tudo e não sobrava registro. **Testes:** `DefaultPaymentCommandHandlerTest` (não suportado não toca o banco; ordem estratégia → save → gateway, com o pagamento gravado; falha do gateway mantém `PENDING` com um único save), decorator (`processPayment` não abre transação), e `TransactionBoundaryTest` com um gateway espião que anota, no instante da chamada, se há transação aberta e se o pagamento já está no banco (falhou antes: "o gateway rodou dentro de uma transação"). **App real** (código commitado × novo, log de `JpaTransactionManager` em DEBUG): antes `Creating new transaction → insert → gateway → Initiating transaction commit`; agora `Creating new transaction → insert → Initiating transaction commit → Closing JPA EntityManager → gateway`. Matriz de 20 requisições de pagamento/webhook idêntica (só varia a ordem das chaves do mapa `errors` do 400 de validação, ordem das violações do Bean Validation). O decorator de Payment segue útil só para o webhook: `confirmPaymentFromWebhook` executa **2 instruções** com a transação (select + update; o merge do `save` acha o pagamento na cache de 1º nível) e **3 sem ela** (medido por mutação; `TransactionBoundaryTest.confirmingAPaymentRunsTwoStatements`). Para o `processPayment` ele não faz nada além de repassar. Suíte: 143 testes.
- [ ] **18. Command side só com portas de escrita.** `RestaurantCommandHandler` usa `KitchenQueryRepository.existsById` e `KitchenCommandHandler` usa `RestaurantQueryRepository.existsByKitchenId`. Mover para `KitchenRepository.existsById(KitchenId)` e `RestaurantRepository.existsByKitchenId(KitchenId)`.
